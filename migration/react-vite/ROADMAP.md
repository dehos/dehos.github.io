## Audit findings and next actions

- Lockfile status was re-audited against the current branch: `migration/react-vite/package-lock.json` is committed and CI runs `npm ci`; the temporary write-capable bootstrap workflow was removed in PR #52. The current workflow has `contents: read` and `persist-credentials: false`.

- Current-stage audit found that brand-target loading accepted `null` and blank strings as numeric zero because JavaScript converts both with `Number(...)`. PR #50 extracts normalization into `src/lib/brand-targets.js`; four deterministic tests reject blank, null, invalid, negative, and non-object persisted values while preserving valid non-negative numeric targets. CI passed dependency audit, stock + brand-target tests, production build, and artifact upload. This remains browser-local storage only and does not touch Supabase.

- The legacy root app checks a Supabase session and queries `app_admins` before initializing the application. In `main/script.js`, that query currently uses `.select("email").limit(1)` without an explicit session-email filter; the client code therefore relies on RLS/query policy to restrict visible rows. This is a source-level finding, not proof of an exploitable access path; RLS and live behavior remain unverified. Do not change production auth without explicit approval.
- A repository-tree audit of `main` found only `build-android-apk.yml` and `react-migration-check.yml` under `.github/workflows/`; no dedicated website deployment workflow was found. GitHub Pages deployment-source settings cannot be confirmed from those files.
- `src/AuthGate.jsx` adds legacy email/password and `login-username` sign-in paths, restores the session, and filters `app_admins` by the current session user's email before rendering the Dashboard. It also checks that returned admin data contains that exact email before granting access; missing email, mismatched rows, or query errors fail closed. This is a client-side defense-in-depth check, not a replacement for Supabase RLS. Password recovery (PR #57) and authenticated password change (PR #58) are merged. Password change requires the current password using the locked Supabase JS `current_password` option, validates new-password confirmation, maps provider errors safely, and attempts global sign-out after success. Live Auth behavior and independent live authorization evidence remain unavailable.
- Password recovery now requests a reset email using the current migration origin/path as `redirectTo`, returns a generic success message to avoid account enumeration, and only allows password updates after a recovery event or recovery-type link restores a session. Successful updates attempt a global sign-out; provider error internals are not exposed. Live delivery, redirect allow-list, and full browser testing remain unverified.
- The Dashboard is currently a visual/data-query first pass only. Its stock arithmetic and relation names have not been validated against real production results; do not treat the displayed totals as parity-approved.
- Brand target settings now allow editing a monthly revenue target for each known brand. Values are stored in this browser's localStorage and update the Dashboard progress display immediately; they do not sync between devices and do not modify Supabase. Brands with no sales still appear with zero progress.

- **Access-control verification** (2026-10-25, rolled-back simulation of the `anon` role, a signed-in non-admin and a signed-in admin; reproducible with `reference/rls-verification.sql`, reference only). RLS is enabled on every public table. All business tables use an admin-only policy keyed on the JWT email matched case-insensitively against `app_admins`; `anon` has no table privileges and cannot execute the write RPCs. Observed: `anon` is refused (permission denied) on `penjualan` and on the sale RPCs; a signed-in non-admin sees 0 rows in `penjualan`/`barang`/`transaksi`/`app_admins`, gets all-zero dashboard totals, is refused when inserting into `barang` or `app_admins`, and the write RPCs cannot find any row to act on; an admin (email upper-cased) sees all 1,259 items, 145 sales and Total Stok 5,660, and sees only their own `app_admins` row. The Dashboard and write RPCs are `SECURITY INVOKER`, so RLS applies to them. The script also confirms the RLS flag and policy names on every public table, that `anon` is refused on the edit and delete RPCs as well, and that the five app-facing functions are `SECURITY INVOKER` (except the unused legacy 5-argument edit overload). It covers database-side RLS and grants only: Supabase Auth settings (sign-up disabled, email delivery, redirect allow-list), the React sign-in flow in a browser and concurrent-write behavior remain unverified.
- **SECURITY FINDING, FIXED 2026-10-26 (owner approved; see "Applied hardening" below):** the `authenticated` role holds `TRUNCATE`, `TRIGGER` and `REFERENCES` on `barang`, `penjualan`, `transaksi`, `brand`, `app_admins` and the import tables. `TRUNCATE` is not subject to row-level security, so any session able to run SQL as `authenticated` could empty those tables. This is not reachable through the standard Supabase REST API (it has no TRUNCATE operation), so it is a defense-in-depth finding rather than a demonstrated exploit, and `anon` has no TRUNCATE (verified). Whether non-admin accounts can exist depends on Auth sign-up settings, which are not visible from the repository. The check was a privilege lookup; TRUNCATE itself was never executed. Recommended owner-reviewed change: revoke `TRUNCATE, TRIGGER, REFERENCES` on those tables from `authenticated` (and keep `anon` as is). This affects the legacy root app too, so test it there first; no migration was written or applied.
- **SECURITY FINDING 2 (2026-10-26, FIXED, see "Applied hardening" below): `public.v_stock` bypassed RLS.** The view is owned by `postgres` without `security_invoker`, and `authenticated` can SELECT it. In a rolled-back session a signed-in non-admin read 0 rows from `barang` but all 1,259 rows (item names and stock levels) from `v_stock`. Neither the legacy app nor the React migration uses the view. The Supabase security advisor also reports this view (ERROR), the unused-policy table `app_login_attempts` (INFO; RLS on with no policy is intentional deny-all) and disabled leaked-password protection (WARN; owner toggle in the Auth dashboard). `reference/proposed-hardening.sql` holds a reviewed, NOT APPLIED fix for this finding and the TRUNCATE/TRIGGER/REFERENCES grants: it was applied inside an always-rolled-back transaction, where non-admin `v_stock` rows went 1,259 -> 0, TRUNCATE was refused, and admin dashboard totals (5,660) plus all four sale/stock RPCs still worked; production was re-checked afterwards and was unchanged. The legacy root app has not been exercised against the change.
- **Applied hardening (2026-10-26, owner approval given in chat):** migration `20261025215734_harden_view_and_revoke_extra_table_privileges` was applied to the live project (recorded in `supabase/migrations/`; same SQL as `reference/proposed-hardening.sql`, which is now historical). Checked on production afterwards: `v_stock` has `security_invoker=true`; `authenticated` keeps only SELECT/INSERT/UPDATE/DELETE on the app tables; `anon`/PUBLIC still have no table grants; in rolled-back sessions a non-admin sees 0 rows in `barang` and `v_stock`, TRUNCATE is refused for both non-admin and admin, and for an admin the dashboard total (5,660) and `catat_penjualan_atomic`, `edit_penjualan_atomic`, `catat_transaksi_stok_atomic` and `hapus_penjualan_atomic` all still work; row counts were unchanged. NOT verified: the legacy root app and the Android build in a browser/device (they do not use `v_stock` and only perform DML), and tables created in future (default privileges were not changed). Still open for the owner in the Supabase dashboard: enable leaked-password protection and confirm email sign-ups are disabled.
- Leftovers observed in a separate read-only catalog inspection (not part of the reference script), not changed: the legacy 5-argument `edit_penjualan_atomic` (SECURITY DEFINER, no EXECUTE grant to `anon`/`authenticated`); `get_penjualan_html()` (read-only, SECURITY INVOKER, executable by `authenticated`, not referenced by this repository); the trigger function `isi_brand_penjualan_otomatis()` (no trigger currently attached, not referenced by this repository).
