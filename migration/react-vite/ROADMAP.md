## Audit findings and next actions

- Current-stage audit confirmed `migration/react-vite/package-lock.json` was absent. PR #51 added a temporary restricted bootstrap mechanism and committed the generated lockfile as `b2489613c7ca26acc72d6b8951a40bd3bdf07810` (lockfile blob `4814580f02af9896b3769fe2162d78db2daddd8b`). PR #52 then removed the write-capable job; final CI has only `contents: read`, `persist-credentials: false`, and passed `npm ci` against the committed lockfile, dependency audit, regression tests, and production build.

- Current-stage audit found that brand-target loading accepted `null` and blank strings as numeric zero because JavaScript converts both with `Number(...)`. PR #50 extracts normalization into `src/lib/brand-targets.js`; four deterministic tests reject blank, null, invalid, negative, and non-object persisted values while preserving valid non-negative numeric targets. CI passed dependency audit, stock + brand-target tests, production build, and artifact upload. This remains browser-local storage only and does not touch Supabase.

- The legacy root app checks a Supabase session and queries `app_admins` before initializing the application. In `main/script.js`, that query currently uses `.select("email").limit(1)` without an explicit session-email filter; the client code therefore relies on RLS/query policy to restrict visible rows. This is a source-level finding, not proof of an exploitable access path; RLS and live behavior remain unverified. Do not change production auth without explicit approval.
- A repository-tree audit of `main` found only `build-android-apk.yml` and `react-migration-check.yml` under `.github/workflows/`; no dedicated website deployment workflow was found. GitHub Pages deployment-source settings cannot be confirmed from those files.
- `src/AuthGate.jsx` adds legacy email/password and `login-username` sign-in paths, restores the session, and filters `app_admins` by the current session user's email before rendering the Dashboard. It also checks that returned admin data contains that exact email before granting access; missing email, mismatched rows, or query errors fail closed. This is a client-side defense-in-depth check, not a replacement for Supabase RLS. Password recovery (PR #57) and authenticated password change (PR #58) are merged. Password change requires the current password using the locked Supabase JS `current_password` option, validates new-password confirmation, maps provider errors safely, and attempts global sign-out after success. Live Auth behavior and independent live authorization evidence remain unavailable.
- Password recovery now requests a reset email using the current migration origin/path as `redirectTo`, returns a generic success message to avoid account enumeration, and only allows password updates after a recovery event or recovery-type link restores a session. Successful updates attempt a global sign-out; provider error internals are not exposed. Live delivery, redirect allow-list, and full browser testing remain unverified.
- The Dashboard is currently a visual/data-query first pass only. Its stock arithmetic and relation names have not been validated against real production results; do not treat the displayed totals as parity-approved.
- Brand target settings now allow editing a monthly revenue target for each known brand. Values are stored in this browser's localStorage and update the Dashboard progress display immediately; they do not sync between devices and do not modify Supabase. Brands with no sales still appear with zero progress.
- The Sales page is merged in PR #43 into `migration/auth-identity-check`; the associated React migration CI run completed successfully. It uses the legacy `catat_penjualan_atomic` RPC for writes, reads existing `penjualan` and `barang` data, and supports month/brand/name filters and CSV export. Edit/delete and Excel/PDF export are not yet ported. Live Supabase behavior remains unverified.
- Stock and In Out merged in PR #44. The React migration build check passed on the final reviewed head. It reads `barang` and `transaksi`, calculates dated balances using the existing `masuk`/`laku`/`adjust_masuk`/`adjust_keluar` movement rules, and writes through `catat_transaksi_stok_atomic`. The UI offers one `adjust` action (the database maps it to the existing internal adjustment movement types), refuses manual stock-out beyond available stock, and directs sales/pre-order flows to Penjualan. No SQL migration or direct table write was added. Live data behavior and balance parity remain unverified.
- PR #45 merged: stock balance arithmetic is extracted into `src/lib/stock-balance.js`; five deterministic Node built-in tests cover initial-stock dates, incoming/sales/legacy adjustments, item/date filtering, negative balances, and invalid quantities. Migration CI runs tests before the build; both passed on the PR head. During review, fixed double-escaped ISO date/month validation patterns in `App.jsx`. These tests do not prove Supabase read/write policies or live data parity.
- CI security hardening merged in PR #46: the migration workflow grants only `contents: read` and disables persisted checkout credentials. CI run #32 passed: dependency install, five stock regression tests, production bundle build, and lockfile artifact upload.
- PR #48 adds `npm audit --audit-level=high` after dependency installation and before tests/build. The PR CI run passed the dependency audit, five stock regression tests, production build, and lockfile artifact upload. This checks known dependency advisories but does not pin versions.
- The CI workflow now runs `npm ci` after generating a lockfile with `npm install`, so CI checks that a clean install from that generated lockfile succeeds. The lockfile is still not committed; this is not yet equivalent to reproducible installs from a reviewed, version-controlled lockfile. Dashboard query/calculation parity and live auth still need independent verification.
- Do not recreate the scaffold or reimplement the already-merged Dashboard UI.
- PR #43 merged successfully; its build check completed successfully. This proves compilation only, not live Supabase parity.

## Safety constraints

- Keep root production files and the current production deployment workflow untouched until cutover.
- No schema, data, RLS, auth, or production query changes without explicit approval.
- Dashboard queries must remain read-only; browser configuration may use only Vite environment variables and the public/anon key, never a service-role key.
- Do not show sample metrics when Supabase is not configured; clearly display connection/setup status.
- A successful build does not prove that production queries, authorization, or calculations match.
- Keep this roadmap updated after each completed step so completed work is not repeated.
